# Subagent Contracts

Reference document for feature-impact-sizing skill. Loaded by the orchestrator before spawning subagents. Defines the 2-pair parallel architecture, input/output contracts, validation rules, and failure handling for all 4 subagents.

---

## Architecture Overview

This skill uses 4 subagents across 2 parallel pairs:

```
Phase 2 complete (problem framing validated)
    │
    ├──── Parallel Pair 1 ────┐
    │                         │
    ▼                         ▼
Research Agent           Scale Data Agent
(runs pipeline,          (structures raw
 extracts benchmarks)     sheet data)
    │                         │
    └──────────┬──────────────┘
               │
               ▼
    Parent: Source tiering (source_tierer.py)
    Parent: Benchmark extraction
    Parent: Scenario construction (decision tree)
               │
    ├──── Parallel Pair 2 ────┐
    │                         │
    ▼                         ▼
Quality Gate             Review Prep Agent
Validator                (formats tables
(10 checks on              for presentation)
 inputs + scenarios)
    │                         │
    └──────────┬──────────────┘
               │
               ▼
    Human Review Gate (Phase 6)
```

**Do NOT parallelize Pair 1 if:** The user's feature description is ambiguous enough that the research queries depend on scale data to be well-targeted (rare — Phase 2 should catch this).

---

## Subagent Prompt Contracts (Universal)

Every subagent prompt MUST include:

1. **The specific data it needs** — pass it, don't make the subagent re-read files
2. **The exact return format** — JSON schema or markdown structure
3. **What it should NOT do** — no calculations, no user interaction, no file writes (unless specified)
4. **A size constraint** — "return in under 500 words" or "return the JSON array only, no commentary"

---

## 1. Research Agent

Runs the research-knowledge pipeline, reads output chunks, and extracts all benchmark candidates with exact quotes. Does NOT tier sources — returns raw extractions.

### Input

| Field | Type | Source |
|---|---|---|
| `feature_description` | string | Phase 1 intake |
| `metric_category` | enum | Phase 1 intake |
| `impact_mechanism` | string | Phase 2 problem framing |
| `search_queries` | array of 5–8 strings | Generated by parent using Phase 3.1 query patterns |

The parent generates the queries because query quality depends on the metric category mapping table in the orchestrator (Phase 3.1).

### Constraints

- Must NOT interact with the user
- Must NOT tier sources
- Must NOT write files outside `/tmp/`
- Return the JSON array only — no commentary, no summaries

### Timeout Policy

The research pipeline typically completes in 15–30 minutes. If the Research Agent has not returned after **45 minutes**, the parent thread presents a **human gate** — do NOT silently proceed:

> "Research pipeline has been running for >45 minutes without completing. Options:
>
> 1. **Retry with fewer queries** — re-run with the top 3 most targeted queries instead of all 5-8. May complete faster with narrower scope.
> 2. **Proceed SME-only** — skip research entirely. Model relies on your SME assumptions only. Confidence capped at LOW. I'll add a `[Research Gap: Pipeline timed out]` risk tag to README row 12.
> 3. **Wait longer** — give the pipeline another 15 minutes.
> 4. **Abort** — stop the sizing. Come back when the pipeline is healthier.
>
> Which would you prefer?"

**Wait for the user's choice.** Do NOT auto-proceed. The PM should decide whether the research gap is acceptable for this sizing's purpose.

### Output

JSON array of benchmark objects (or error):

```json
[
  {
    "source_title": "McKinsey Warehouse Automation Report 2025",
    "url": "https://...",
    "improvement_type": "percentage",
    "improvement_value": 0.12,
    "exact_quote": "Companies implementing X saw 12% reduction in...",
    "context": "Survey of 200 warehouses, >50K daily orders, North America"
  }
]
```

If the pipeline fails or returns no results:

```json
{
  "benchmarks": [],
  "pipeline_error": "description of failure"
}
```

## 2. Scale Data Agent

Structures raw sheet data into the output schema, applies Data Source Priority rules (see `references/data-sources.md`), and flags cross-source conflicts. **Does NOT call MCP** — the parent pre-fetches all raw data and passes it in.

### Architecture Note

The parent thread makes all `read_sheet_values` MCP calls before spawning this agent (see orchestrator Phase 4 for ranges). The agent receives raw cell values and applies structuring, unit normalization, and conflict detection. This is more robust than having the subagent call MCP directly — MCP tool inheritance in subagents is not guaranteed.

### Input

| Field | Type | Source |
|---|---|---|
| `metric_category` | enum | Phase 1 intake |
| `scope` | sites array | Default `["OH", "AZ"]` |
| `process_steps` | array | For `labor_cost` only — from Phase 1 intake |
| `raw_sheet_data` | JSON objects | One per MCP read, keyed by `source_tab` — parent pre-fetches |

### Constraints

- Must NOT call MCP
- Must NOT interact with the user
- Must NOT write files
- Return the JSON object only — no commentary

### Output Schema

```json
{
  "metric_category": "labor_cost | shipping_cost | fulfillment_cost | quality | turnaround",
  "scope": { "sites": ["OH", "AZ"], "products": "all" },
  "volumes": {
    "annual_total": 0,
    "by_site": { "OH": 0, "AZ": 0 },
    "by_product": { "Non-WL": 0, "Oral": 0, "GLP-1": 0, "Novo Pen": 0, "Novo Pills": 0 },
    "source": "D&F TPH | Trans_Summary | D&F_Summary",
    "period": "FY26 (Jan-May ACT, Jun-Dec blank)"
  },
  "baselines": {
    "primary_metric": { "value": 0, "unit": "$ | tasks/hr | %", "source": "tab!range", "period": "FY26" },
    "per_unit_metric": { "value": 0, "unit": "$/fill | $/shipment", "source": "tab!range" },
    "by_step": [
      { "step": "Pack", "uph": 30.5, "hourly_rate": 28.00, "annual_hours": 70247, "annual_dollars": 1285795, "source": "D&F TPH (primary) | Win Calculator (fallback)" }
    ]
  },
  "labor_data": {
    "regular_dollars": { "pharmacy": 0, "fulfillment": 0, "source": "D&F TPH" },
    "ot_dollars": { "pharmacy": 0, "fulfillment": 0, "source": "D&F TPH" },
    "hsv_dollars": { "pharmacy": 0, "fulfillment": 0, "source": "D&F TPH" },
    "total_pay": 0,
    "variable_cost_per_fill": { "OH": 0, "AZ": 0 }
  },
  "conflicts": [
    { "field": "pack_uph", "source_a": "Win Calculator", "value_a": 34, "source_b": "TPH Tracker", "value_b": 30.5, "delta_pct": 10.3, "recommendation": "Use TPH Tracker (actuals)" }
  ]
}
```

Fields not applicable to the metric category should be `null` (e.g., `labor_data` is `null` for `shipping_cost`). The `conflicts[]` array is always populated — empty array means no conflicts found.

## 3. Quality Gate Validator

Runs 10 structured checks against both the raw inputs (research + scale data) AND the proposed scenarios. Produces a single PASS / WARN / FAIL report that the parent surfaces in the Human Review Gate.

This replaces the previous two-pass design (Findings Validator + Plausibility Validator). Running all checks in one pass after scenario construction eliminates a full subagent round and removes overlapping checks.

### Input

| # | Field | Source |
|---|---|---|
| 1 | Research Agent full output (benchmarks array or `pipeline_error`) | Parallel Pair 1 |
| 2 | Scale Data Agent full structured output | Parallel Pair 1 |
| 3 | Proposed scenario assumptions table (variable, Low, Base, High, rationale per factor) | Parent scenario construction |
| 4 | SME assumptions array from Phase 1.5 (or empty array) | Intake |
| 5 | Feature description | Phase 1 |
| 6 | Metric category and process steps | Phase 1 |
| 7 | Physical Limits Reference Table | From `references/data-sources.md` — parent passes it in |
| 8 | Extracted benchmarks with tiers and applicability ratings | Phase 5 (source tiering) |

### Constraints

- Read-only — no user interaction, no file writes, no MCP calls
- Return the JSON report only, no commentary
- Under 800 words total (including JSON)

### 10 Checks

#### Check 1: Quote Accuracy

**What it catches:** Misquoted or fabricated benchmarks.

| PASS | WARN | FAIL |
|---|---|---|
| Every `exact_quote` contains the claimed `improvement_value` (as substring or semantic equivalent, e.g., "12%" matches "12 percent") | ≥1 quote does not contain its claimed value but the value appears elsewhere in the `context` field | A claimed `improvement_value` appears in neither the `exact_quote` nor the `context` — the number may be fabricated |

#### Check 2: Scale Data Reasonableness

**What it catches:** Anomalous baselines from bad MCP reads or wrong cell ranges.

| PASS | WARN | FAIL |
|---|---|---|
| All values fall within expected ranges (see table below) | ≥1 value is outside expected range but within 2× of the boundary (possibly data entry error or scope artifact) | Any value is negative, zero when it shouldn't be, or >5× outside expected range (e.g., Pack TPH of 300) — indicates a bad MCP read or wrong cell range |

**Expected ranges** (sourced from [teammate], FP&A — May 27, 2026 finance discovery session + TPH Tracker actuals):

| Metric | Expected Range | Source |
|---|---|---|
| TPH (any role) | 10–55 | TPH Tracker FY26 actuals |
| Pharmacist TPH | 60–90 | TPH Tracker OH FY avg: 71.1 |
| Variable cost per fill (hourly labor) | $3.50–$5.00 | [teammate] `[Q-009]` |
| Fully loaded cost per fill | $8–$14 | [Director of Pharmacy & Fulfillment Product] `[Q-010]` — ~$10-12 typical |
| Pack associate hourly rate | $25–$32 | [teammate] `[Q-011]` — ~$28 FTE, ~$23.50 temp |
| Pharmacist hourly rate | $90–$110 | Win Calculator — $99.78 |
| Tech hourly rate | $30–$42 | Win Calculator — $36.00 |
| Annual shipment volume (single site) | 2M–8M | D&F_Summary FY26 — OH ~5M, AZ ~4M. Below 2M likely partial/weekly read; above 8M likely multi-site total |
| Improvement % (any category) | 0–60% | Physical Limits Table ceiling |

#### Check 3: Data Freshness

**What it catches:** Thin sample baselines that make extrapolation risky.

| PASS | WARN | FAIL |
|---|---|---|
| FY average/total is based on ≥12 weeks of actuals (≥25% of year) | FY value is based on 4–11 weeks of actuals (8–24% of year) — flag extrapolation risk | FY value is based on <4 weeks of actuals (<8% of year) or all values are forecast/blank — baseline is unreliable |

**Compounding special case:** If `metric_category` involves compounding (cost per tablet), WARN regardless of week count and note: "Compounding baselines have a batch-release timing lag — tablets count only when QA releases the batch, not when produced. Weekly data is inherently noisy. Use rolling 30-day or MTD windows instead." (Source: [teammate], FP&A — batches can lag 1-2 weeks between production and QA release.)

#### Check 4: Conflict Verification

**What it catches:** False or missed cross-source conflicts in the Scale Data Agent output.

| PASS | WARN | FAIL |
|---|---|---|
| Every `conflicts[]` entry has `delta_pct` correctly computed as `abs(value_a - value_b) / min(value_a, value_b) × 100`. No obvious conflicts are missing (e.g., if Win Calculator and TPH Tracker both have UPH for the same step, a conflict entry exists if they differ by >5%) | A conflict entry has `delta_pct` off by >2 percentage points from recalculated value (rounding or unit mismatch) | A conflict entry's `delta_pct` is wrong by >10 points, OR two sources have the same metric for the same step differing by >5% with no conflict entry |

#### Check 5: Physical Plausibility

**What it catches:** Impossible improvements that exceed physical or operational limits.

| PASS | WARN | FAIL |
|---|---|---|
| High scenario implies metrics below 80% of ceiling from Physical Limits Reference Table | High scenario implies metrics between 80% and 100% of ceiling | High scenario implies metrics at or above ceiling (e.g., Pack TPH ≥ 55, improvement % ≥ 60%, adoption ≥ 100%) |

#### Check 6: Addressable Base

**What it catches:** Savings that exceed the total cost being addressed.

| PASS | WARN | FAIL |
|---|---|---|
| High impact < baseline cost for affected scope | High impact > 50% of baseline (unusual but possible) | High impact > 100% of baseline cost — saving more than exists |

#### Check 7: Source Quality + Independence (2 sub-checks)

**What it catches:** Circular reasoning and inapplicable comparisons.

This check has two sub-results that roll up to the check's overall result (worst of the two):

**Sub-check 7a: Independence**

| PASS | WARN | FAIL |
|---|---|---|
| Different sources used for benchmark and sanity check | Only one source, but it's A-tier with explicit methodology | Same data point used for both the benchmark AND the baseline validation |

**Sub-check 7b: Applicability**

| PASS | WARN | FAIL |
|---|---|---|
| ≥1 benchmark rated HIGH applicability from comparable context (scale, industry, regulated) | All benchmarks MEDIUM applicability or from adjacent industries | All benchmarks LOW applicability or from fundamentally different contexts (e.g., retail → pharma) |

**Roll-up:** `result = worst(7a.result, 7b.result)`

#### Check 8: SME-Benchmark Alignment

**What it catches:** Unresolved conflicts between internal estimates and external data.

| PASS | WARN | FAIL |
|---|---|---|
| SME range and benchmark range overlap or are within 2× | SME and benchmarks diverge >2× but the decision tree resolved it with documented rationale | SME and benchmarks diverge >3× with no documented resolution — the model may be anchored to the wrong signal |

**Normalization rules** (SME assumptions and benchmarks may express improvement in different units):

1. **If both are percentages:** Compare directly. Divergence = `max(a, b) / min(a, b)`.
2. **If one is absolute and one is percentage:** Convert absolute to percentage using the baseline. E.g., "$0.40/script savings" with baseline "$4.39/fill" = 9.1% improvement.
3. **If both are absolute but different units:** Convert both to percentage of the relevant baseline, then compare.
4. **If conversion is not possible** (incompatible units, missing baseline): Return WARN with detail: "Cannot normalize SME assumption ([unit A]) against benchmark ([unit B]) — manual review required." Do NOT return FAIL for a normalization failure.

**If no SME assumptions exist:** Auto-PASS this check (nothing to compare).

#### Check 9: Scenario Consistency + Double-Counting (2 sub-checks)

**What it catches:** Broken scenario logic and inflated impact from overlapping factors.

This check has two sub-results that roll up to the check's overall result (worst of the two):

**Sub-check 9a: Internal Consistency**

| PASS | WARN | FAIL |
|---|---|---|
| Low < Base < High for every variable factor; rationales align with values | Scenario spread is unusually tight (<2× between Low and High) or wide (>5×) | Low > Base or Base > High for any factor; or rationale contradicts the value |

**Sub-check 9b: Double-Counting**

| PASS | WARN | FAIL |
|---|---|---|
| Each factor represents an independent lever; no factor pair shares a cost base | Two factors are conceptually related but the overlap is <20% of impact | Two or more factors share a cost base and the multiplicative model inflates the result (e.g., `improvement_pct` and `efficiency_gain` both reducing the same labor pool) |

**Shipment-numerator distortion (critical — must check):** All roles use shipments as the numerator. An initiative that increases downstream throughput (e.g., pack) will cause ALL upstream TPH rates (pharmacist, tech) to appear to improve — because more shipments get out the door. This is a metric artifact, NOT a real upstream improvement. If the sizing claims savings in multiple process steps from a single-step initiative, FAIL this check unless the initiative genuinely improves each step independently. (Source: [teammate] FP&A walkthrough, confirmed by [PM] and [Ops Program director] — "if the shipment doesn't get out, all of your pharmacist labor gets carried forward.")

**Roll-up:** `result = worst(9a.result, 9b.result)`

#### Check 10: Factor Redundancy

**What it catches:** A variable factor that double-counts a scope or adoption constraint already embedded in a constant factor's derivation.

| PASS | WARN | FAIL |
|---|---|---|
| Every variable factor represents an independent lever not already captured in a constant's derivation | A variable factor partially overlaps with a constant's embedded assumption but the overlap is <20% of impact | A variable factor is conceptually redundant with a scope/volume/adoption constraint in a constant's derivation — the multiplicative model inflates the result by applying the same discount twice |

**Common trigger:** A constant like `annual_dispatch_labor_value` is built from per-leg volume percentages that represent the automatable share. Adding a separate `adoption_rate` variable factor double-counts adoption — the leg %s already capture it. Similarly, if `addressable_labor` is scoped to internal sites only, a separate `site_adoption_rate` that excludes 3PLs is redundant.

**How to check:** For each variable factor, read the constant factor(s)' `derivation.components` or `derivation.inputs`. If any component name or value implies the same scope constraint the variable factor represents (e.g., "40% of 79201 totes" in a component name while `adoption_rate` is a separate variable), FAIL.

**Overlap with Check 9b:** Check 9b (double-counting sub-check) and Check 10 both catch factor overlap, but at different abstraction levels. Check 9b catches *conceptual* cost-base sharing ("two factors reduce the same labor pool"). Check 10 catches *structural* derivation overlap ("variable factor duplicates a component in a constant's derivation"). A Check 10 FAIL will almost always also trigger a Check 9b FAIL, but the reverse is not true — Check 9b can catch conceptual overlap that isn't visible in derivation components. Both checks are intentional; the overlap is by design. S10 (Phase 7.1) provides a third layer on the same territory, catching double-counting that survives the human review gate (Phase 6).

### Output Format

```json
{
  "checks": [
    {
      "id": 1,
      "name": "Quote accuracy",
      "result": "PASS | WARN | FAIL",
      "detail": "One sentence explaining the finding.",
      "evidence": "The specific values or quotes that drove the result.",
      "affected_benchmarks": [0] | null,
      "suggested_action": null | "Specific fix if WARN or FAIL"
    },
    {
      "id": 7,
      "name": "Source quality + independence",
      "result": "WARN",
      "detail": "Independence passed but all benchmarks are medium applicability.",
      "evidence": "...",
      "sub_checks": [
        { "name": "independence", "result": "PASS", "detail": "..." },
        { "name": "applicability", "result": "WARN", "detail": "..." }
      ],
      "suggested_action": "Consider additional research from regulated healthcare sources."
    },
    {
      "id": 9,
      "name": "Scenario consistency + double-counting",
      "result": "PASS",
      "detail": "All factors ordered correctly and independent.",
      "evidence": "...",
      "sub_checks": [
        { "name": "internal_consistency", "result": "PASS", "detail": "..." },
        { "name": "double_counting", "result": "PASS", "detail": "..." }
      ],
      "suggested_action": null
    }
  ],
  "summary": {
    "pass_count": 0,
    "warn_count": 0,
    "fail_count": 0,
    "blocking": true | false
  }
}
```

**Counting rules:** 10 top-level checks. `pass_count + warn_count + fail_count == 10`. Each merged check (7, 9) counts once at its roll-up level. `blocking: true` if any check is FAIL.

`affected_benchmarks` is an array of indices into the Research Agent's benchmarks array (for Check 1 only) — helps the parent identify which benchmarks to drop or re-verify.

## Output Validation

The parent thread MUST validate subagent output before consuming it:

| Subagent | Validity Check | If Validation Fails |
|---|---|---|
| **Research Agent** | Output is a JSON array with ≥0 items. Every item has non-null `source_title`, `url`, and `improvement_value`. | Log warning. Proceed to Phase 5 with empty benchmarks — this triggers the "No benchmarks found" error path. |
| **Scale Data Agent** | Output has non-null `volumes.annual_total` and ≥1 non-null entry in `baselines`. `metric_category` matches what was requested. | Block. Re-run Phase 4 sequentially in the parent thread (direct MCP reads). Do NOT proceed with partial data. |
| **Quality Gate Validator** | Output has `checks` array with exactly 10 items. Each item has `result` matching `PASS`, `WARN`, or `FAIL`. `summary.pass_count + summary.warn_count + summary.fail_count == 10`. | Run the 10 checks manually in the parent thread. Checks 1–4 are mechanical (substring match, range check, week count, delta recalculation). Checks 5–10 require the Physical Limits Table and scenario assumptions. |
| **Review Prep Agent** | Output contains markdown with ≥3 table headers (`|`-delimited rows). | Format the tables manually in the parent thread. Low severity — cosmetic only. |

## How the Parent Thread Uses the Quality Gate Report

1. **All PASS:** Proceed to Human Review Gate. Mention: "Quality gate passed — no issues found."

2. **WARN only:** Present warnings alongside the scenario tables in the Human Review Gate. Ask user to confirm they're acceptable. Warnings are informational, not blocking.

3. **Any FAIL:** Present the failure(s) to the user BEFORE showing the scenario tables. Ask for revised assumptions or explicit override with rationale. Do NOT show the scenarios as-is — they contain a structural problem.

   **Common FAIL resolutions:**

   | Check | Common Fix |
   |---|---|
   | 1 (Quote accuracy) | Drop the affected benchmark(s) from the extraction. Re-run scenario construction without them. |
   | 2 (Scale data reasonableness) | Re-read the sheet with corrected ranges. Or ask user for a manual baseline override. |
   | 3 (Data freshness) | Ask user for an alternative baseline source. Or narrow scope to weeks with actuals only. |
   | 4 (Conflict verification) | Re-run the Scale Data Agent with explicit conflict detection instructions. |
   | 5 (Physical plausibility) | Reduce the High scenario assumption to below the ceiling. |
   | 6 (Addressable base) | Narrow scope (fewer sites, specific product) or reduce improvement assumptions. |
   | 7 (Source quality) | Run additional targeted research. Or acknowledge low-quality sources and cap confidence. |
   | 8 (SME-benchmark alignment) | Surface the conflict to user. Ask which signal should anchor the model. |
   | 9 (Scenario consistency) | Fix Low/Base/High ordering. Or separate overlapping factors into independent models. |
   | 10 (Factor redundancy) | Remove the redundant variable factor; the constant's derivation already captures the mechanism. |

4. **Unresolvable FAIL:** If the user cannot fix the underlying issue AND does not want to override, **abort the sizing and pivot to a validation path recommendation.** Output a short report:
   - Feature description and why the sizing could not be completed
   - Which quality gate check(s) failed and why they are unresolvable
   - A specific validation recommendation (time study, pilot, vendor demo, process observation) with estimated effort and timeline
   - Do NOT produce a dollar impact estimate — an unfounded number is worse than no number

5. **User override of FAIL:** If the user explicitly overrides a FAIL check, document it: `[Override: User accepted [check name] FAIL — rationale: "..."]`. Cap confidence at MEDIUM regardless of other signals.
